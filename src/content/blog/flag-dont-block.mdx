The workflow: suppliers send invoices for work done on a customer's assets. Parts, labour, VAT, a reference number, sometimes a scanned photo of a printout taken at an angle in a badly lit workshop. Someone has to read each one, check the customer isn't being overcharged, and approve it.

Two obvious things you'd like software to do here. Read the invoice, and notice when it's wrong.

The second one is where teams get into trouble, because "notice when it's wrong" quietly becomes "reject it", and now a language model is refusing to pay a real supplier for real work over a price it half-understood.

The design rule that makes the whole thing tractable is one line: **the model annotates, humans decide.** Everything below is what falls out of taking that seriously.

## Why "block" is the tempting mistake

Blocking feels like the responsible choice. If the system is confident an invoice is fraudulent, why let it through?

Because of the asymmetry in what each error costs.

A **false flag** costs someone fifteen seconds. They look at it, see the part really did cost more this time because it's a different manufacturer, dismiss it with a note, and move on.

A **false block** costs you a supplier relationship, a phone call, an escalation, and a permanent institutional belief that "the AI thing doesn't work". Worse, it's silent from the supplier's side: they don't know they've been rejected by a model, they just know they haven't been paid.

And the rates aren't symmetric either. In a domain with genuine variance — parts prices move, suppliers rename SKUs, labour times vary by how seized the bolt was — an anomaly detector tuned to catch real fraud will produce many more false positives than true ones. That's fine for a flag. It's disqualifying for a block.

There's a second reason, less obvious and more important in the long run: **a flag is a training signal, a block is a dead end.** Every dismissal with a reason is a labelled example telling you the check is too tight. Blocks don't generate that data, because the humans downstream never see the case — they just see an angry email.

So: no automated rejection, ever. The strongest thing the system may do is refuse to *auto-approve*, and route to a human with its reasoning attached.

## Tiered extraction: cheapest path that works

An LLM is not a document parser. It's the last tier of one.

**Tier 1 — the embedded text layer.** Most supplier invoices are generated by accounting software and exported as PDFs with a perfectly good text layer. Pull it out with a library. It's free, instant, deterministic, and correct. Skipping straight to a vision model here is paying for and waiting on a worse version of something you already have.

**Tier 2 — OCR.** Scans and photos need pixels turned into characters. Still deterministic, still cheap, still no model involved in *understanding* anything. You now have text of variable quality.

**Tier 3 — the model, for structure only.** Text in, structured line items out. This is the one job in the pipeline that genuinely needs a language model, because the thing that varies is layout and phrasing, and that's exactly what they're good at.

```go
func (s *Service) Extract(ctx context.Context, doc Document) (Extraction, error) {
	// Tier 1: embedded text. Free, exact, most common case.
	if text, ok := pdf.EmbeddedText(doc); ok && looksComplete(text) {
		return s.structure(ctx, text, SourceEmbedded)
	}

	// Tier 2: OCR the pixels.
	text, err := s.ocr.Run(ctx, doc)
	if err != nil {
		return Extraction{}, fmt.Errorf("ocr: %w", err)
	}
	if !looksComplete(text) {
		// Don't spend a model call on a page that's clearly half-scanned.
		// A human gets it with an honest "we couldn't read this".
		return Extraction{Status: NeedsManualEntry}, nil
	}

	// Tier 3: structure it.
	return s.structure(ctx, text, SourceOCR)
}
```

The `NeedsManualEntry` branch matters more than it looks. The pipeline is allowed to give up. Systems that must always produce output are systems that produce fiction on the bad inputs, and the bad inputs are exactly where fiction is most expensive.

Record which tier produced each extraction. When you're debugging a wrong line item eight weeks later, "did this come from a text layer or a photo of a fax" is the first question and you don't want to be guessing.

## Never let the model do arithmetic

If you take one implementation detail from this post, take this one.

Ask the model for line items — description, quantity, unit price. Do **not** ask it for the subtotal, the VAT, or the total. Compute those yourself, in integer pence, from the line items it extracted.

```go
// Totals are arithmetic, not inference. The model reads the page; the code
// does the maths. Anything the model claims about totals is treated as a
// second opinion to compare against, never as the value we store.
var subtotal int
for _, li := range extracted.LineItems {
	subtotal += li.Quantity * li.UnitPricePence
}
vat := ComputeVAT(subtotal, doc.VATRateBps)
total := subtotal + vat
```

Then use the printed total on the invoice — which you also extracted — as a **check**, not as a source:

```go
if extracted.PrintedTotalPence != nil && *extracted.PrintedTotalPence != total {
	flags = append(flags, Flag{
		Type:     FlagTotalsMismatch,
		Severity: SeverityHigh,
		Detail: fmt.Sprintf("line items sum to %s, invoice states %s",
			money(total), money(*extracted.PrintedTotalPence)),
	})
}
```

This single check earns its keep three ways: it catches genuine supplier arithmetic errors, it catches the model missing a line item entirely (the sum comes up short), and it catches OCR mangling a digit. One comparison, three failure modes, zero trust extended to anything probabilistic.

The general form of the rule: **let the model do perception, never computation.** Reading "4 × brake pad @ £42.50" off a page is perception. Multiplying it is not.

## Canonical parts behind an alias table

To compare prices over time you need to know that `BRK-PAD-FRT`, `Front Brake Pads (set)`, and `BRAKE PAD FRONT AXLE KIT` are the same thing. Three suppliers, three names, one part.

The wrong move is letting the extractor create parts. Do that and within a month your catalogue has forty variants of a brake pad, every price history is fragmented across them, and no anomaly check can work because there's no history to compare against.

Two tables, and a hard rule about who may write to each:

```sql
CREATE TABLE canonical_parts (
  id          bigserial PRIMARY KEY,
  account_id  bigint NOT NULL REFERENCES accounts(id),
  code        text NOT NULL,
  name        text NOT NULL,
  category    text NOT NULL,
  UNIQUE (account_id, code)
);

CREATE TABLE part_aliases (
  id                bigserial PRIMARY KEY,
  account_id        bigint NOT NULL REFERENCES accounts(id),
  supplier_id       bigint REFERENCES suppliers(id),
  raw_text          text   NOT NULL,          -- exactly as printed
  canonical_part_id bigint REFERENCES canonical_parts(id),
  confirmed_by      bigint REFERENCES users(id),   -- NULL = proposed
  confirmed_at      timestamptz,
  UNIQUE (account_id, supplier_id, raw_text)
);
```

The flow:

1. Extraction produces `raw_text` for each line.
2. Look it up in `part_aliases`. Confirmed hit → canonical part, done, no model call.
3. Miss → the model *proposes* a match against the existing catalogue, with a confidence. The proposal is written as an unconfirmed alias row.
4. A human confirms or corrects it, once. From then on it's a lookup.

Notice the shape: **the model's output is a suggestion attached to a row a human will approve, and approval is what makes it real.** `confirmed_by IS NULL` is the entire boundary between "a machine thought this" and "we believe this".

The economics are good too. Alias tables saturate fast — after a few hundred invoices from a supplier, nearly every line is a cached hit, and model calls fall to near zero for that supplier. The expensive path is only for genuinely new text.

Never auto-create a canonical part. If the model can't match, the line stays unmapped and someone maps it. An unmapped line is a small, visible gap. A wrongly-created canonical part is invisible and poisons every comparison downstream.

## Flags are rows, not exceptions

A flag is a first-class record, with enough structure that a human can act on it in seconds:

```sql
CREATE TABLE invoice_flags (
  id            bigserial PRIMARY KEY,
  invoice_id    bigint NOT NULL REFERENCES invoices(id) ON DELETE CASCADE,
  line_item_id  bigint REFERENCES invoice_line_items(id) ON DELETE CASCADE,
  flag_type     text NOT NULL,
  severity      text NOT NULL,          -- info | warning | high
  detail        text NOT NULL,          -- human-readable, with the numbers in it
  evidence      jsonb NOT NULL,         -- what it compared against
  source        text NOT NULL,          -- 'rule' | 'model'
  dismissed_by  bigint REFERENCES users(id),
  dismissed_at  timestamptz,
  dismiss_reason text,
  created_at    timestamptz NOT NULL DEFAULT now()
);
```

Four columns there are doing real work:

**`detail` contains the numbers.** "Unit price £84.00 is 62% above the 12-month median of £51.80 across 9 invoices." Not "unusual price". A reviewer should be able to make the call from the flag text without opening anything else, and vague flags are ignored flags.

**`evidence`** holds what it compared against — the median, the sample size, the invoice ids. That's what makes the flag auditable, and what lets you tune a threshold later using real cases instead of intuition.

**`source`** separates rule-derived from model-derived. More on that next.

**`dismiss_reason`** is your feedback loop. Every dismissal is a labelled false positive. Group by `flag_type` and sort by dismissal rate, and the checks that need loosening sort themselves to the top. A flag type running at 90% dismissal isn't a check, it's noise, and it's teaching reviewers to click through everything without reading.

Flags never mutate the financial record. They don't change amounts, don't set status, don't hold up payment on their own. They're an annotation layer over an immutable extraction.

## Deterministic checks and model checks are different citizens

Both write flags. They are not the same thing and shouldn't be presented as one.

**Rules** are arithmetic and history. Totals mismatch. Duplicate line item within one invoice. Same supplier reference seen before. Unit price outside N% of the trailing median for that canonical part. Labour hours above the published standard time for that operation. Every one is a deterministic function, reproducible, explainable in a sentence, and cheap enough to run on every invoice.

**Model checks** are for the things rules can't see. Is this part plausible for this asset type? Does the described work match the labour lines? Does the narrative on the page contradict the itemisation?

Two consequences of the distinction:

**Rules always run. Model checks may fail open.** If the provider is down or slow, the invoice still processes with its rule flags and a note that the model pass didn't complete. What you must never do is silently skip the model pass and present the result as fully checked. Absent is fine; pretending is not.

**Their severities live on different scales.** A totals mismatch is arithmetic — it's high severity and it is *certain*. A model saying "this part looks unusual for this asset" is a hint. Rendering both as an identical red badge trains reviewers to distrust the red badge, which costs you the arithmetic one.

## Reproducibility: pin everything, store everything

Extraction is versioned, because it will change and you need old invoices to keep meaning what they meant:

```sql
CREATE TABLE invoice_extraction_versions (
  id            bigserial PRIMARY KEY,
  invoice_id    bigint NOT NULL REFERENCES invoices(id) ON DELETE CASCADE,
  raw_text      text NOT NULL,           -- exactly what the model saw
  tier          text NOT NULL,           -- embedded | ocr
  model_id      text,                    -- pinned model id, never an alias
  prompt_version text,
  payload       jsonb NOT NULL,          -- structured output as returned
  created_at    timestamptz NOT NULL DEFAULT now()
);
```

Rules that come out of this:

**Store the raw text, always.** It's the input. Without it, you can't reproduce anything, and re-running OCR later gives you a different string on the same file.

**Pin the model id.** Not a floating alias that silently rolls forward. A pipeline whose behaviour changes because a vendor shipped an update, on an invoice run you can no longer reproduce, is not a system anyone can audit.

**Version the prompt and store which one ran.** The prompt is code. It belongs in the repo, in review, with a version string that lands in this table.

**Never overwrite.** Re-extraction appends a new version row. The old one stays, along with the flags it produced and whatever a human decided about them.

Keep a small evaluation set — thirty or so real invoices with known-correct extractions, including the ugly ones — and run it before shipping any prompt or model change. Not a research benchmark, just the version of "does the pipeline still work" that survives the fact that the pipeline is nondeterministic.

## Operational bits that matter more than the prompt

**Give the feature its own API key.** `INVOICE_OCR_OPENAI_API_KEY`, not a shared `OPENAI_API_KEY` used by three features. Per-feature keys mean per-feature spend attribution, per-feature rate limits, and — the day it matters — the ability to revoke one capability without taking down the other two. Sharing one key across features is the same mistake as sharing one database user across services, and it's discovered the same way: during an incident.

**Cap the spend per document.** One invoice must never trigger an unbounded retry loop against a paid API. Bound the attempts, bound the tokens, and fail to `NeedsManualEntry` when the bound is hit.

**Log cost per invoice.** Not aggregate monthly spend — per document, alongside the tier that handled it. That's how you discover that 3% of documents are consuming half the budget because they're photos of photos, and that the fix is a UI hint about scanning, not a cheaper model.

**Make review fast.** All of this is in service of a human looking at flags and clicking through them. If the flag list takes four seconds to load, or the evidence is a page away, the reviewer will approve without reading and every check you've written becomes decorative.

---

The whole architecture reduces to one sentence: **probabilistic components may add information; only deterministic code and humans may change outcomes.**

Extraction adds structure to a document. Aliasing proposes a mapping a human confirms. Flags add annotations a human resolves. The arithmetic is arithmetic, the approval is a person, and the model — for all the work it's doing — never once decides whether anybody gets paid.
